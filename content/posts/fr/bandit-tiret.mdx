## Contexte

Première semaine, premier challenge sérieux. Je fais Bandit sur OverTheWire, une série de niveaux d'introduction au shell Linux. Le niveau 1 → 2, ça devait prendre 30 secondes : se connecter en SSH, lire un fichier, récupérer le mot de passe.

Le fichier s'appelle `-`.

Je tape `cat -`. Le terminal se fige. Plus rien. Aucune erreur, aucune sortie. Juste un curseur qui clignote et attend.

J'ai passé plusieurs minutes à penser que ma connexion SSH avait un problème.

## Ce que j'ai fait

Voilà exactement ce qui s'est passé :

```bash
bandit1@bandit:~$ ls
-
bandit1@bandit:~$ cat -
```

Le terminal entre en attente d'input clavier. `cat -` est une convention Unix : `-` signifie "lis depuis l'entrée standard (stdin)", pas depuis un fichier. La commande attend que je tape quelque chose au clavier.

La solution : ajouter `./` devant pour que `-` soit traité comme un chemin de fichier, pas comme stdin.

```bash
bandit1@bandit:~$ cat ./-
[mot de passe récupéré]
```

Ça fonctionne aussi avec la redirection :

```bash
bandit1@bandit:~$ cat < -
[mot de passe récupéré]
```

Ou encore avec `--` pour signaler la fin des options :

```bash
bandit1@bandit:~$ cat -- -
[mot de passe récupéré]
```

## Ce que j'ai appris

**Le shell interprète les arguments avant de les passer à la commande.**

Quand je tape `cat -`, le shell ne passe pas le caractère `-` à `cat` comme nom de fichier. Il suit une convention POSIX : `-` en argument = stdin. Aucune erreur, aucun avertissement. C'est le comportement attendu.

En ajoutant `./`, je passe un chemin (`./` = répertoire courant), et le shell n'a plus rien à interpréter. C'est clairement un fichier.

En développement normal, on ne crée vraiment jamais de fichiers nommés `-` ou qui commencent par `--`. En sécurité, c'est exactement le genre de cas limite qui peut piéger un script mal écrit ou montrer comment un système gère vraiment ses inputs.

Premier niveau, première leçon : ne jamais supposer qu'un argument sera interprété comme un nom de fichier.
